# FEM · Revisión de seguridad y despliegue · 13 octubre 2026

## Alcance y estado

El proyecto Vercel `web-fem` incorpora tienda, checkout propio, admin, CRM y contador mediante cuatro servicios. La vista previa remota responde en las rutas principales. Los cobros y la creación de pedidos están bloqueados hasta completar la validación de pagos. El dominio oficial femprobiotics.co no se modificó. El proyecto Supabase Web-Fem nuevo está vacío; no se migraron clientes ni pedidos a él.

## Aplicado y comprobado

- Build Vercel: servidor como Function, recursos estáticos en public/__theme, Node 24.x, TypeScript con typeRoots explícito. Se resolvió el error de carpeta public.
- Cabeceras: HTTPS/HSTS en Vercel, nosniff, SAMEORIGIN, Referrer-Policy, Permissions-Policy y CSP limitada para base/object/frame. No equivale a una CSP estricta de scripts.
- Contraseña del admin local: hash scrypt con sal en archivo privado; sesión aleatoria, HttpOnly, SameSite=Strict, caducidad, revocación y límite de intentos. Secure cuando el origen configurado es HTTPS. En Vercel las sesiones se guardan como hashes SHA-256 en una tabla con RLS; el secreto interno se configura como variable privada. En local es aleatorio por arranque.
- Restricción de métodos, comprobación de Origin, precios y productos del carrito tomados del servidor; la selección anticipada no acepta contraentrega.
- CRM: eliminado el respaldo literal de JWT, cron rechaza si falta secreto y webhook Meta rechaza si falta secreto de firma. No se cambió la interfaz de asesoras.
- Archivos CRM: gateway permite multipart de hasta 17 MB para un archivo de 16 MB más overhead; el CRM conserva autenticación, rol, línea WhatsApp, MIME, límites y ventana de conversación. No se habilitaron cargas públicas. En Vercel Functions existe además el límite de solicitud de 4,5 MB: los adjuntos grandes requieren carga directa autenticada a almacenamiento antes de igualar los 16 MB del CRM original. Antivirus y comprobación completa de contenido binario pendientes.
- Confirmación Mercado Pago: comprueba external_reference, importe COP y método del pedido antes de actualizarlo.
- Consentimiento: banner con rechazar/aceptar y posibilidad de retirar; trackers conocidos se eliminan del HTML antes del consentimiento y cookies opcionales conocidas no se retransmiten. Se requiere auditoría de red completa de scripts anidados/terceros para certificar todos los trackers.
- Checkout: consentimiento de tratamiento necesario separado del opcional; tracking de carrito condicionado al consentimiento; Meta IDs y eventos del cliente condicionados; CAPI exige consentimiento explícito y se persiste marketing_consent para el webhook. Columnas privacy_consent_at y marketing_consent agregadas a orders de la base de checkout, verificadas por consulta.
- RLS: las ocho tablas del checkout ya lo tenían. Se habilitó RLS y retiraron privilegios anon/authenticated en siete tablas internas del CRM. Consulta posterior: cero tablas public sin RLS. Acceso de backend preservado. SQL aplicado conservado en migrations/ por proyecto.
- Escaneo: 1.047 objetos de texto de Git revisados por patrones; única coincidencia era imagen base64 (falso positivo). 15 secretos configurados buscados en código y 61 bundles del navegador: ninguna coincidencia. Esto no certifica ausencia de cualquier secreto desconocido. No se reescribió el historial ni rotaron claves porque no se confirmó ninguna filtración.
- Dependencias: checkout actualizado a Next 16.4.0, compilación correcta; CRM a Next 16.4.0 y React 19 con adaptación de params asíncronos; compilación remota correcta. La tienda no tiene vulnerabilidades de producción según npm audit.
- Pruebas: 11 tests de privacidad/autenticación/integración; 14 tests de storefront en la rama de despliegue; las 10 fases HTTP locales pasan tras reiniciar módulos. Navegador: política de cookies, rechazo persistente y home funcional.

## Pendientes que bloquean la salida completa

1. CRM: tras migrar Next, npm audit conserva 0 critical, 5 high y 2 moderate; revisar dependencias restantes y regresión de todos los flujos de atención. Checkout: 2 moderate por dependencia transitiva del SDK Mercado Pago, requiere actualización mayor del SDK y probar pagos.
2. Protección distribuida contra intentos/bots. Las sesiones del admin ya se comparten mediante base de datos. Los límites actuales en memoria son locales, no equivalen a WAF/CAPTCHA ni resisten un reinicio. No se ha configurado CAPTCHA.
3. Cifrado de campos sensibles adicional al de infraestructura: no implementado. Requiere diseño de llaves, rotación y migración compatible con búsqueda/CRM. No se deben hashear direcciones ni claves API que el servidor necesita recuperar.
4. Arquitectura y secretos privados configurados en Vercel. Falta completar pruebas de negocio con usuarias reales, archivos grandes y proveedores.
5. Supabase advisors CRM: search_path mutable en conversations_sync_ultimo_mensaje, pg_trgm en public y protección contra contraseñas filtradas desactivada. No se trasladó pg_trgm sin revisar dependencias de búsquedas. Monitorización continua/alertas de consultas aún no configuradas.
6. Políticas existentes responden 200: privacidad de GRUPO MSM S.A.S., reembolsos y términos. Nueva política de cookies incorporada. Confirmar datos empresariales/canales vigentes y revisar texto legal; no se afirma cumplimiento legal certificado.
7. Reseñas: no se añadieron reseñas ficticias ni se certificó autenticidad individual. Falta vincular/verificar el origen Trust y auditar widgets.
8. Contraste/teclado: banner y checkbox accesibles; falta auditoría WCAG completa. El contraste no garantiza aprobación de Meta, que depende también de permisos/configuración y cumplimiento de sus políticas.
9. Admin global mantiene contraseña compartida; para producción necesita usuarios individuales, roles, MFA y auditoría. CRM conserva sus roles por usuaria. API internas aún requieren revisión completa de autorización por objeto, esquema de entradas y minimización de respuestas.

Las claves publicables y los identificadores de píxel pueden ser públicos; service_role, tokens de proveedores y secretos de firma nunca deben enviarse al navegador. Integraciones de terceros deben declararse en privacidad; ocultarlas o hashear sus IDs no aporta seguridad.
